## HIGH-1 · ids and names disagreed on 46% of relations

`schema_v3.py` `build_graph()`

```python
key = tuple(sorted([s.lower(), t.lower()]))        # alphabetical sort
si, ti = name2id.get(key[0], -1), name2id.get(key[1], -1)   # ids from the sorted order
rel_rows.append({..., "src_id": si, "tgt_id": ti,
                 "src_name": v["s"], "tgt_name": v["t"], ...})  # names from the original order
```

`si`/`ti` came from the **alphabetically sorted** pair, `src_name`/`tgt_name` from the **original
order**. Whenever the alphabetical order differed from the original, the pairing broke.

```
   measured   of 12,764 relations, 5,994 (46%) had
              the entity named by src_id ≠ src_name

   example    src_name 'Superhuman AI'  →  src_id pointed to 'Industrial Revolution'
```

The graph is undirected so the edges themselves were fine, but **what the cards and the graphml
displayed was wrong.**

**Fix** — take the id and the name from the same source.

```python
si = name2id.get(v["s"].lower(), -1)
ti = name2id.get(v["t"].lower(), -1)
```

### Side finding — 395 relations with a `-1` endpoint

Surfaced while fixing the above. The LLM **used names in relations that were not in its own
entity list** (violating rule 7 of the extraction prompt). `-1` is handled silently everywhere
downstream:

```
   export_graph.py       not in keep, so filtered — disappears from the graph
   export_kal_graph.py   same
   relation_vec          ent_docs.get(-1, []) → half of the 1-hop expansion
   degree aggregation    skipped by the i >= 0 check (degree is correct)
```

Everything is handled defensively, but **nobody is told.** Since the rows are unusable, they are
now dropped and the count reported. Relations 12,764 → 12,369.

**Verified**: 0 broken endpoints · 0 id/name mismatches · 0 degree mismatches

## HIGH-2 · a truncated PEM private key slipped past masking

`ingest_sessions.py`

```python
("PRIVATE_KEY", re.compile(r"-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]{0,4000}?-----END [A-Z ]*PRIVATE KEY-----"))
```

It **requires** `-----END`. Session logs frequently have tool output cut off midway, leaving only
the header plus part of the body — and that does not match.

```
   pattern check   header+body      masked ✅
                   header only      missed ❌   ← the real case
                   header+truncated body   missed ❌
```

It was actually found in one distilled document
(`oh-my-airs-플러그인-배포-자동화…`). That said, **that instance had no body** — zero base64
lines, the value truncated to something like `7185…`, and the document itself was a **security
incident record** saying "a secret was exposed, act within 48 hours".

**Fix** — added a pattern that catches the END-less variant. The complete-block pattern has to
come first so that the END is also removed, so the declaration order is preserved.

## MEDIUM-2 · the docs did not admit two statistical limitations

**The BH correction does not account for the size of the search** (`tune_alpha.py:154`)

```python
cand = rows[:8]                       # after evaluating a 146-point grid
ps = [wilcoxon_signed_rank(...)]      # look at the results, take the top 8
rej, adj = benjamini_hochberg(ps, 0.05)
```

BH corrects **for those 8 only**. The selection bias of the 146-point search remains. The top 8
are extreme values by definition, so their p-values are optimistic.

**The held-out split is not an independent sample.** It halves the same 58 queries, so it shares
the corpus, the answer key, and the judge. It catches weight overfitting but not answer-key bias.

## Fix — an honest protocol

`tune_alpha.py --protocol --seeds 20`

```
   split the 58 queries into A/B
     A (selection)  evaluate the 146-point grid and take the winner.  B is not looked at
     B (test)       compare only that winner against the baseline.  one test → no multiple comparisons
   repeat 20 times with different seeds to remove split luck
```

**Measured**

```
   test-set Δ (vs. baseline)   median +0.116 · range [+0.069, +0.149]
   significantly better        19 of 20 (95%)
   splits with Δ > 0           20 of 20 (all)

   BH applied across all 146   significantly better in 139 (95%)
```

The selection-set value (+0.125) and the test-set value (+0.116) are nearly the same. **The
conclusion survived.** What changed is not the number but the grounds for believing it.

Side observation — the winner chosen on set A differed every time
(`(0.1,0,0.3,0.6)` ×5 · `(0.2,0,0.2,0.6)` ×4 · `(0.2,0.2,0,0.6)` ×4). That means **the top of
the ranking is statistically indistinguishable**, consistent with the earlier observation that
"the top 12 are effectively tied".

L15 (the held-out split being a division of the same 58 queries) **still stands.** Bias in the
answer key itself (L1) is not something this protocol can catch.

## MEDIUM-3 · graph view — 87% of labels crowded into the centre

```
   all nodes             radius median 62 · max 106
   the 110 labelled      radius median 38 · p90 64 · max 75
   → 87% inside the overall median radius
```

Hubs have high mass (`mass = 1 + degree`) so the layout keeps them central, and labels were
picked purely by top degree. **There was no way to know what was out at the edges.**

**Fix** — divide the screen into a 190×86 grid and take the highest-degree node per cell.
What surfaced from the periphery: `Integration 테스트` · `프론티어 모델` · `CSS 변수` ·
`PlantUML` · `세무사법 개정` · `masterfile.xlsx` · `경쟁 지형 분석`.

Fixed at the same time:
- label collision was judged with a fixed 74px width, so long names overlapped → measured with
  `measureText`
- the degree slider was capped at 12 (actual max 116) → now derived from the data's p99.5
- the plugin compared `nodeCap` against the **pre-filter** length (`ents.length`) → `keepIdx.length`
- favicon 404 (the only console error)
